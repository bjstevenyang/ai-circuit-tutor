# 用需求 PR 与实现 PR 交付一个阶段

GitHub PR 是工作流状态来源，PRD 是产品需求来源，CR 是变更记录来源；不维护另一份 STATUS 索引。阶段 2、3、4 各一对 PR，共六个阶段 PR，顺序推进。当前流程规范 PR 不计入这六个 PR。

## PR A：Requirement Change PR

1. 核对仓库、HEAD、工作区、已验证实现基线和用户授权，保留无关修改。获得分支授权后从更新后的 master 创建独立 `codex/` 需求分支。
2. 复制 [CR 模板](TEMPLATE.md)，定义问题、包含／排除范围、前后行为、验收 ID 差异与待决事项，更新 PRD；涉及模型、状态或存档时同步相应文档。创建 Draft 需求 PR，只包含文档，不修改业务代码。
3. Codex 只读分析代码、依赖、模型、存档和测试风险，将影响报告提交到该需求分支。Work 可依据 PR 材料审查需求清晰度，所有结论回到需求 PR。
4. 需求和影响报告稳定后记录待批准的完整 head SHA，请用户审阅该版本。用户批准并合并需求 PR，正式形成新需求基线；Rejected 则停止依赖实现。批准后内容若变化须重新审阅，不能沿用旧批准。

## PR B：Implementation PR

1. 确认需求 PR 已经用户批准并合并，更新本地主线，再创建独立 `codex/` 实现分支，不复用需求分支。
2. 在实现 PR 记录需求 PR 链接、CR ID、验收 ID、用户批准依据和实际采用的完整需求基线 SHA。该 SHA 必须在主线及实现分支历史中，且包含批准后的需求。squash／rebase 合并时记录合并后 SHA 和原批准 head SHA 的对应关系，不能误用未进入主线的原 head 作为基线。
3. 读取固定 SHA 下的 CR、PRD 和相关模型／设计，比较验收差异，输出实施前确认报告。无冲突且授权覆盖时继续实现，无需用户重复批准同一范围；批准缺失、需求不明或版本不符时停止依赖工作并报告。
4. 在实现分支提交代码、测试及实际验证记录。逐项提供验收 ID → 测试文件／场景 → 命令与结果，列出人工验证和未完成项。新增或改变产品要求须另走需求 PR，不能在实现 PR 中静默修改批准基线。
5. Work 对照已合并需求版本审查覆盖；Codex 审查代码质量；CI 验证测试与需求映射。分别记录执行者、代码 SHA 和实际结果，新提交后重做受影响检查。Verified 只覆盖实际执行部分。
6. 用户最终验收并决定是否合并实现 PR；代理不自动合并。下一阶段从更新后的主线开始下一对 PR。

需求批准／合并 SHA 放在 PR 记录及后续实现确认中，不要求需求文件引用它自己的未来 commit。需求 PR 合并前不得启动依赖该需求的业务代码实现。

## Codex 执行入口及自动化边界

用户提供已合并需求 PR 链接并要求继续实施后，Codex按上述检查创建实现 PR。提供实现 PR 时读取其关联需求基线继续工作。PR 创建本身不会自动启动任务；无法核实批准时等待用户，不依赖 Work 聊天记录。

未来触发器 A 处理需求 PR 的 ready／更新事件并输出只读影响报告；触发器 B 处理实现 PR 的创建／提交更新，执行验证和审查。按 PR 类型及已处理 SHA 去重，机器人反馈不触发同类循环。批准后自动启动实现是额外执行集成，不能由这两类检查推定已实现。

当前没有为本流程配置新事件触发器、认证、费用预算或分支保护，未执行的审查不能标成通过。Work 与 Codex 的报告分别回到对应 PR，跨 PR 通过明确链接和 commit 交接。

## 小型变更例外

提示文字错别字等不改变产品行为／电气规则／验收的微小修正，以及已批准行为的范围内缺陷修复，可使用单个实现 PR，记录原验收和授权依据，不制造第二次产品审批。本次流程文档 PR 属于已明确授权的规范调整，不额外创建实现 PR。应用测试按 TEST_PLAN 执行，浏览器仅 Chromium。
