# 用一个 PR 交付一个需求或阶段

GitHub PR 是工作流状态来源，PRD 是产品需求来源，CR 是变更及证据记录。无需维护另一份 STATUS 索引。阶段编号不等于已批准实施。

## 新需求到合并

1. 核对工作区、HEAD、已验证实现基线和用户授权；有无关修改先保留。获得分支授权后从最新已合并主线创建 `codex/` 分支。
2. 复制 TEMPLATE.md 创建有唯一 ID 的 CR；填写需求范围、前后行为、验收差异和待决项。提交需求草案并创建 Draft PR，以 PR 模板填写输入。此时不改业务代码。
3. 只读分析实现、依赖、模型、存档和测试，将影响报告提交到该分支。需求文档和报告稳定后，记录待批准的完整 commit SHA，请用户批准此版本。Proposed → Impact Analysis。
4. 用户在 PR 中明确批准 SHA 与范围，或将可核实的用户批准依据记录进 PR。Approved 不表示合并或免除最终验收；Rejected 则停止实施并记录原因。普通批准评论若没有明确版本，不作为实施依据。
5. Codex 接手时读取 PR、CR、指定 commit 及 PRD 差异，确认该 commit 存在于分支历史、批准覆盖范围、无未决冲突，记录 Acknowledged 报告。随后在同一分支实现已批准内容；新决策重新审批受影响部分。
6. 逐项提交验收证据、回归结果、人工检查及未完成项，更新 PR 描述。需求覆盖与代码质量审查分别记录执行者和被审查代码 SHA；新增提交后判断并重做受影响检查。Verified 只覆盖实际执行部分。
7. 用户验收最终代码版本后决定合并。合并前不启动依赖该成果的下一阶段；下一阶段从更新后的主线重新建分支和 PR。

需求批准 commit 不需要改写以填写它自己的 SHA：批准记录放在 PR 评论和之后的确认报告中。需求变更后产生新 commit，旧批准不会自动覆盖新要求。

## Codex 的执行入口

用户提供 PR 链接并要求“核对已批准需求并继续实现”后，Codex 可执行以上确认和实施步骤；PR 创建本身不会启动任务。没有批准则仅分析、补文档并报告阻塞。PR/CR 信息不足时，先补齐信息，不依赖 Work 的聊天记录。

Work 的需求审查、Codex 代码审查和 CI 结果均回到同一 PR。当前没有为本流程配置新的事件触发器；未实际执行的审查不能标成通过。凭据、权限、事件过滤、去重 SHA、错误恢复和自动化预算需另行设计与授权。
